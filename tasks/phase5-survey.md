## §1 What exists and can be reused

- **The SBOM is already stored, once per analysis** (`Sbom.document`, a
  CycloneDX 1.6 JSON validated structurally by `analysis/sbom.py`, capped at
  32 MiB and 20 000 components, generated by Syft with `--network none`,
  metadata only). Components carry `name`, `version`, `purl`, `licenses[]`
  as Syft emits them. The inventory READS this row; it never regenerates it
  (CLAUDE.md → Forbidden).
- **The E3 triage already stores the VEX input.** An SCA finding carries
  `advisory = {id, package, version, fixed, ecosystem}` and the analyst's
  `verdict` (`confirmed` / `false_positive`) with its written justification.
  A VEX document is a projection of those rows — no new write path, no new
  role decision.
- **A local OSV database already ships for OSV-Scanner** (P1):
  `scripts/osv_db_download.sh` fetches `<Ecosystem>/all.zip` from
  `osv-vulnerabilities.storage.googleapis.com` on a connected host. The
  mirror table of P5 is fed by the SAME dump format (a zip of one OSV JSON
  record per advisory), so the air-gap contingency ("import the dump by
  file") and the scheduled sync parse identical bytes.
- **Two hostile-input parsers to copy from**: `ingest/archive.py` (entry
  count, declared vs streamed size, decompression ratio, zip-slip) for the
  OSV zip, and `analysis/sbom.py` (`_parse` with byte cap, shape checks with
  caps) for every JSON record.
- **The queue boundary is closed by an allowlist** (`core/queue.py::ALLOWED_JOBS`,
  JSON serializer, callbacks refused). Two jobs are added there — sync and
  import — and that edit is a security decision recorded here, because the
  worker is the process that holds the Docker socket. Neither new job starts
  a container; the sync is the ONLY job that opens an outbound connection.
- **RQ ships a scheduler** (`rq worker --with-scheduler`, `enqueue_in`,
  `enqueue_at`): no `rq-scheduler` dependency. A job with a fixed `job_id`
  is replaced, not duplicated, when scheduled again.
- **The audit trail is append-only at the database level** and every phase
  writes its rows; what is missing for "full audit log" is a READ endpoint
  scoped by role and the Bitácora screen (mockup 10). `audit.service` has
  `entries_for_actor`; an admin-wide read does not exist yet.
- **The report context is one serializable dict** (`reports/context.py`) and
  every renderer consumes it; sections 7–10 are new keys in that dict plus
  template blocks, with `strings.json` holding their Spanish prose (the
  CLAUDE.md carve-out). The E5 layout (`workflow/diagrams.py::layout`) is
  computed SERVER-SIDE with integer coordinates, so the annex SVG is a
  ~60-line emitter over the same `Layout` — never the browser's SVG.
- **`analysis/cvss.py`** already turns a CVSS 3.1 vector into a score and a
  severity; OSV records carry vectors, NVD records carry both.
- **The mockups exist**: screen 11 (Inventario) and screen 10 (Usuarios y
  bitácora). Every class they use (`cards`, `card`, `rowline`, `prio`,
  `checkline`, `ck`, `badge`, `progress/pbar/pfill`, `radio`, `nextstep`,
  `panel`, `actions`) already exists in `frontend/src/theme/components.css`.
  Progress widths use the stepped `w0…w100` classes (CSP forbids inline
  style). Both tabs are always visible in the mockups' tabs bar, not only
  when the route names an analysis.

## §2 Threat model deltas

| Delta | Why it matters | Control |
|---|---|---|
| **Outbound sync** — the first process of the platform that opens a connection to the internet | A covert channel out of the factory; a live third-party dependency in disguise; a poisoned dump | Runs ONLY in the worker as an RQ job, never in a request; the two base URLs are settings (`DIOPTRA_VULNDB_OSV_BASE_URL`, `DIOPTRA_VULNDB_NVD_BASE_URL`) with HTTPS enforced by a validator and NEVER settable through the API; `ssl.create_default_context()` (TLS verification on, system CA store), a connect/read timeout, a download byte cap (`vulndb_max_dump_bytes`), redirects refused (`urllib` opener without `HTTPRedirectHandler`), the response streamed to a spool file then parsed with the same guards as an operator import; `DIOPTRA_VULNDB_SYNC_ENABLED=false` disables it entirely (air gap) and the panel then says so and offers only the import; every sync writes an audit row with its outcome and a `vulndb_syncs` row with the counts; the "Actualizar la base ahora" button only ENQUEUES |
| **Dump import** — a new file-upload ingestion surface | A hostile zip (bomb, slip, entry flood) or a hostile JSON (size, nesting, a record whose fields are huge) reaches the database or the panel | The request handler streams the upload to a spool file under `vulndb_spool_dir` with the ZIP byte cap and REFUSES to parse it: the worker job parses it. Zip: `zipfile` with entry-count cap, per-entry declared and streamed size caps, ratio cap, names ignored entirely (only the JSON content matters, so zip-slip has nothing to slip into — entries are read into memory, never extracted to disk). JSON: NVD feeds are streamed record by record with `JSONDecoder.raw_decode` over a bounded buffer (a 300 MB yearly feed never lands in memory at once); every field is capped at persistence (`summary` 2 000 chars, ≤ 200 aliases, ≤ 500 affected packages, ≤ 200 versions and ≤ 50 ranges each); a record that does not fit the shape is COUNTED and skipped, never raised on; the spool file is deleted whatever happens |
| **Vulnerability text in the panel and the PDF** | OSV summaries and NVD descriptions are third-party prose; component names/versions/licenses/PURLs are the audited lockfile's | Same rule as snippets: stored raw, escaped at every render (React text nodes, Jinja2 autoescape, DOCX text runs). Neither the panel nor the report ever renders a URL from a record as a link — references are printed as text |
| **CSV export** | Formula injection: a component named `=HYPERLINK(...)` opens in Excel | Every cell that starts with `=`, `+`, `-`, `@`, `\t`, `\r` is prefixed with `'`; cells are quoted; the encoder is `csv` with `QUOTE_ALL` |
| **Correlation cost** | 20 000 components × a few thousand advisories per package name could be quadratic | The join is indexed: `vulnerability_packages(ecosystem, name)`; per component one query, and version comparison in Python over ≤ 200 versions + ≤ 50 ranges per advisory. The panel is factory-wide; the overview is computed per request over the LATEST analysis per project only (trend uses the previous one) and capped at `MAX_INVENTORY_COMPONENTS` = 50 000 across projects, with the cap recorded in the response |
| **Audit log read** | A developer reading the analyst's verdict history, or an analyst reading another analyst's actions, is information disclosure the matrix forbids | `GET /api/v1/audit`: admin reads everything; analyst and developer read ONLY rows whose `actor_username` is theirs. Filters are `since` (ISO) and a `limit` ≤ 500. Justifications are the writer's own text and render as text |
| **The runtime role can `DROP TRIGGER`** (accepted residual since P0) | Append-only is only as strong as the role that connects | Day 20: `docker/initdb/01-roles.sql` creates `dioptra_app` with no ownership and only DML grants; `alembic upgrade` runs as the owner (`POSTGRES_USER`), the API and worker connect as `dioptra_app` (`DIOPTRA_DATABASE_URL` vs `DIOPTRA_MIGRATION_DATABASE_URL`). Proven in the `migrations` CI job: `DROP TRIGGER` as `dioptra_app` fails |

## §3 Design — data model (migration `0009_inventory`)

```
vulnerabilities
    id            str(64) PK      -- OSV id ("GHSA-…", "PYSEC-…") or "CVE-…" when only NVD knows it
    source        'osv' | 'nvd'
    aliases       JSON [str]      -- the CVE ids and cross-ids, capped 200
    summary       Text ≤ 2000     -- OSV summary / NVD English description
    score         float | null    -- CVSS 3.x base score (OSV vector via cvss.py, or NVD baseScore)
    vector        str(120) | null
    severity      'critical'|'high'|'medium'|'low'|'info'|null
    published_at, modified_at  UtcDateTime | null
    withdrawn     bool
    fixed_versions JSON {"<ecosystem>/<name>": [versions]}   -- for "outdated"
    synced_at     UtcDateTime

vulnerability_packages           -- the indexed join, one row per affected package
    id            uuid PK
    vulnerability_id  FK → vulnerabilities.id ON DELETE CASCADE
    ecosystem     str(40)         -- OSV ecosystem name ("npm", "PyPI", "Packagist", "Maven", "Go")
    name          str(255)        -- OSV package name (Maven: "group:artifact")
    versions      JSON [str] ≤ 200      -- explicit affected versions
    ranges        JSON [{type, events:[{introduced|fixed|last_affected}]}] ≤ 50
    INDEX (ecosystem, name)

vulndb_syncs                     -- what the panel shows as "copia local del …"
    id, source ('osv'|'nvd'|'import'), started_at, finished_at, status ('ok'|'failed'|'partial'),
    records_seen, records_stored, records_skipped, detail ≤ 500, requested_by_username | null
    -- last_update = max(finished_at) where status in ('ok','partial')

crypto_assets                    -- the CBOM, per analysis
    id, analysis_id FK CASCADE, algorithm str(80), primitive str(40) ('hash'|'cipher'|'mac'|'signature'|'kdf'|'random'|'protocol'),
    path str(1024), line int|null, weak bool, rule_id str(200)
```

No table for components: the SBOM document is the source, parsed per request
(bounded by the 20 000-component cap it was stored under). A `components`
table would be a second copy of the SBOM that could drift from the document
the report attaches.

## §4 Design — the vulnerability mirror

```
sync job  (app.inventory.sync.run_sync_job, in ALLOWED_JOBS)
    if not settings.vulndb_sync_enabled: record 'skipped' and return
    for eco in settings.vulndb_osv_ecosystems (default npm, PyPI, Packagist, Maven, Go):
        download f"{osv_base}/{eco}/all.zip" → spool (TLS, no redirects, timeout, byte cap)
        import_osv_zip(spool)            # same function the file import uses
    for year in settings.vulndb_nvd_years (default: the last 3 calendar years; [] disables NVD):
        download f"{nvd_base}/nvdcve-2.0-{year}.json.gz" → spool
        import_nvd_feed(spool)           # streamed, gzip-aware
    write vulndb_syncs row per source; audit 'vulndb.sync' (actor "system" or the requester)
    if settings.vulndb_sync_interval_hours > 0:
        queue.enqueue_in(interval, SYNC_JOB, job_id="vulndb-sync")   # fixed id → replaced, never duplicated

first schedule
    API lifespan: if sync enabled → enqueue_in(60 s, SYNC_JOB, job_id="vulndb-sync") — idempotent by id;
    the job itself returns early when the last successful sync is younger than the interval,
    so several API replicas or restarts cost one no-op job, never a download storm.
    Worker command gains --with-scheduler.

import job (app.inventory.sync.run_import_job, in ALLOWED_JOBS)
    path = spool_dir / f"{token}.{kind}"          # token is a uuid the handler generated; kind ∈ {osv-zip, nvd-json, nvd-json-gz}
    parse with the same importer; delete the file in `finally`; vulndb_syncs row source='import'

upsert semantics
    by id: a record whose `modified` is older than the stored `modified_at` is skipped (idempotent re-import);
    packages of an updated record are replaced wholesale (delete + insert, inside the record's transaction);
    batches of 500 records per commit so a 100 000-record feed never holds one transaction.

version matching  (app.inventory.versions)
    parse(version) → tuple of (int | str) segments after stripping a leading "v", split on . - + ;
    numeric segments compare as ints, non-numeric as strings after numbers (so 1.0.0-rc < 1.0.0 is FALSE
    under this comparer — recorded: prerelease ordering is NOT modelled; a prerelease is compared as its
    numeric prefix plus a lower string tail → 1.0.0-rc < 1.0.0 holds because ("1","0","0") < ("1","0","0","rc") is
    reversed explicitly: a version with extra non-numeric tail is ORDERED BEFORE its numeric prefix)
    affected(component_version, package_row):
        if version in package_row.versions: True
        for range in ranges (type SEMVER or ECOSYSTEM; GIT ranges ignored — no commit hash to compare):
            introduced = first 'introduced' event ("0" means everything); fixed / last_affected the next event
            if introduced <= v and (fixed is None or v < fixed) and (last_affected is None or v <= last_affected): True
        False
    unparsable component version → NOT matched, and the component is listed under "versión no comparable"
```

Why OSV is the correlation source and NVD the enrichment: OSV records name
packages by ecosystem + name (and PURL) with explicit version events — that
is what a lockfile-derived SBOM can be joined on. NVD names products by CPE,
which does not map onto PURLs without a curated dictionary the platform does
not have. So: an NVD record is stored under its CVE id with score, vector,
severity and description; at correlation time an OSV match whose `aliases`
contain a CVE id borrows the NVD score when OSV carries none. An NVD-only
record is never correlated by itself — the panel says so in its footnote.

## §5 Design — correlation, "outdated", statistics

```
components_of(sbom.document) → [Component(name, version, purl, ecosystem, license_ids[], type)]
    ecosystem from the PURL type (npm→npm, pypi→PyPI, composer→Packagist, maven→Maven with "group:artifact",
    golang→Go, cargo→crates.io, gem→RubyGems, nuget→NuGet); a component without a PURL is listed, never correlated

correlate(db, components) → [Match(component, vulnerability, fixed_in, vex_state, justification)]
    rows = select vulnerability_packages where (ecosystem, name) in the components' keys   (one IN query per ecosystem)
    for each component × row: if affected(...) → Match; fixed_in = the smallest 'fixed' event > version, if any
    vex_state from the analysis' SCA findings: same package name AND (advisory.id == vuln.id or in vuln.aliases)
        confirmed → 'exploitable', false_positive → 'not_affected' (with the analyst's justification as detail), None → 'in_triage';
        no finding at all → 'in_triage'

latest_known(component) = max over parse(): every 'fixed' event stored for that package
                          ∪ every version of the same (ecosystem, name) in any OTHER stored SBOM of the factory
outdated ⇔ latest_known > component.version
    -- honest offline signal, not the registry's latest; the panel's card says "frente a la última versión
       conocida en la copia local", which is exactly the mockup's own wording

overview(db) → for the LATEST analysis with an SBOM of every project (+ the previous one for the trend):
    totals: components, projects, vulnerable components, open CVEs (vex_state != not_affected), outdated, by severity,
    by license (top 8 + "sin licencia"), by project rows (name, version label = analysis.created_at date, components,
    outdated, open CVEs, trend = open CVEs now − open CVEs previous), crypto summary (algorithms, weak count),
    vulndb_last_update (from vulndb_syncs), sync_enabled, capped flag.
    "version" of a project analysis = the analysis' ordinal within the project ("v3 · 22-09-2026") — the
    platform has no semantic version of the audited system; the mockup's "v1.3" is illustrative.
```

## §6 Design — CBOM, VEX, exports

**CBOM tool decision**: OUR OWN SEMGREP CRYPTO-INVENTORY RULES. cdxgen's CBOM
output needs Node + a 200 MB dependency tree inside the analysis image and
covers a subset of the languages; IBM cbomkit is a Java service with its own
database. Both are Apache-2.0, both are a new image to ship air-gapped for
one column of the panel. Semgrep already runs over every audited tree with
our rules, so the CBOM is one more rule file (`rules/semgrep/crypto-inventory.yml`)
whose results the normalizer DIVERTS into `crypto_assets` instead of
findings:

```
rule metadata: {crypto: {primitive: "hash", algorithm: "$ALG"}, inventory: true, cwe: none, owasp: none}
   -- the metavariable is resolved by Semgrep into result.properties? NO: Semgrep does not template metadata.
   -- Therefore one rule per (algorithm family) with a metavariable-regex on the algorithm literal, and the
      normalizer reads the ALGORITHM FROM THE MATCHED TEXT (result.message carries the interpolated $ALG; Semgrep
      DOES interpolate metavariables in `message`). Message format the rules commit to: "crypto: <primitive> <ALG>".
normalizer: a SARIF result whose rule has properties.metadata.inventory == true → CryptoAsset(primitive, algorithm
   normalised upper-case, path, line, weak = rule.metadata.weak == true); it never becomes a Finding.
   The existing weak-crypto.yml rules keep producing FINDINGS (they carry CWE-328/330): a weak algorithm is BOTH
   a finding for triage and a `weak` asset in the CBOM. Same match, two purposes, two rules — deliberate.
CBOM document (CycloneDX 1.6): bomFormat/specVersion/serialNumber/metadata.timestamp + components[] with
   type "cryptographic-asset", name = algorithm, cryptoProperties = {assetType: "algorithm", algorithmProperties:
   {primitive, ...}}, evidence.occurrences = [{location: path, line}]. One component per distinct algorithm,
   occurrences listed. Certificates / protocols: only what a rule can see in source (a `.pem` reference, a
   `TLSv1`/`SSLv3` literal) — recorded as primitive "certificate" / "protocol" when matched, else absent.
VEX document (CycloneDX 1.6): bomFormat/specVersion + vulnerabilities[] = one per Match: id, source {name: "OSV"|"NVD"},
   ratings [{score, severity, method: "CVSSv31", vector}], affects [{ref: component bom-ref or purl}],
   analysis {state, detail: justification}. State mapping as in §5.
Exports: GET …/analyses/{id}/sbom (exists) · GET …/analyses/{id}/cbom · GET …/analyses/{id}/vex · GET …/analyses/{id}/components.csv
   Content-Disposition file names from the project name through the existing report_file_name sanitiser.
```

Acceptance of the plan ("SBOM valid against the 1.6 schema"): the SBOM is
Syft's own output, validated structurally by `analysis/sbom.py`; the CBOM
and VEX emitted here are checked by a NEW structural test that asserts the
1.6 shape the spec requires for `cryptographic-asset` and `vulnerabilities`
(bomFormat, specVersion, required keys, enums), with the same "our own check,
no JSON-Schema dependency" rule P1 recorded.

## §7 Roles (written into docs/roles-and-permissions.md before the endpoints)

| Action | admin | analyst | developer |
|---|---|---|---|
| Read the inventory panel, per-project rows, open CVEs, CBOM summary | ✓ | ✓ | ✓ |
| Download SBOM / CBOM / VEX / CSV | ✓ | ✓ | ✓ |
| Request a vulnerability-database sync (`POST /inventory/vulndb/sync`, written reason) | ✓ | ✓ | — |

| VEX verdicts | — | via E3 triage only (no new endpoint) | — |
| Read the audit log (`GET /audit`) | everything | own actions | own actions |

The developer needs the inventory to plan tests (a vulnerable dependency is a
malicious-case candidate) and to read the report, so reading is open to the
three roles, like the report export. Refreshing the mirror is an operator
act with an audit row, so it is the admin's and the analyst's — the analyst
because the mockup shows `mmarin` on that screen with the button and because
a signed report depends on the mirror's date.

**Deviation recorded**: the matrix says the analyst reads the audit log of
"own projects"; v1.0.0 narrows that to "own actions". A project→analyst
ownership does not exist in the data model (projects have `created_by_id`
only through the analysis), and inventing it on the last days would be a new
authorization surface without a survey. Recorded in the scope-change log.

## §10 Decisions taken here (reversible before the commit)

1. **Cut**: PHP/Java to a second cycle (§9).
2. **CBOM tool**: our own Semgrep crypto-inventory rules (§6); cdxgen and
   cbomkit rejected on footprint, not licence.
3. **Mirror design**: OSV is the correlation source, NVD the enrichment (§4).
4. **"Outdated"** = a newer version known to the local copy (a fixed
   version in an advisory, or another project's SBOM) — never a registry
   query (§5).
5. **Sync scheduling**: RQ's own scheduler, a self-rescheduling job with a
   fixed id, kicked once by the API lifespan; `DIOPTRA_VULNDB_SYNC_ENABLED`
   off = air gap (§4).
6. **Roles** as in §7, including the audit-log narrowing to own actions.
7. **Mockup 10's "Usuarios" half is not built** (no endpoint, not in the plan).
